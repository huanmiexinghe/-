# 部署运维手册（Linux 生产环境）

适用对象：Magnetic Rush 联机中继的 Operator。客户端打包与代码协作见仓库根目录 [CONTRIBUTING.md](../CONTRIBUTING.md)。

生产服务器：阿里云 Linux（Ubuntu 22.04 / 24.04 或 Debian 12），公网 `47.96.190.73`，中继以 systemd 服务常驻。

> 本文不含任何真实密码、token 或玩家数据。`relay.env`、`accounts.json`、签名文件只在服务器和密码管理器里，不进仓库。

---

## 1. 生产环境现状

| 项目 | 实际值 |
|---|---|
| systemd 服务名 | `magnetic-rush-relay` |
| unit 文件 | `/etc/systemd/system/magnetic-rush-relay.service` |
| 运行用户 / 组 | `magnetic-rush` / `magnetic-rush`（`/usr/sbin/nologin`，不可登录） |
| 程序目录 | `/opt/magnetic-rush`（`root:root`，运行时只读） |
| 数据目录 | `/var/lib/magnetic-rush`（`magnetic-rush:magnetic-rush`，`0750`） |
| 配置文件 | `/etc/magnetic-rush/relay.env`（`root:magnetic-rush`，`0640`） |
| 备份目录 | `/var/backups/magnetic-rush`（`root:root`，`0700`） |
| 日志 | journald，`journalctl -u magnetic-rush-relay`（不写日志文件） |
| 监听 | 当前内测直连：`HOST=0.0.0.0`、`PORT=8080`，即 `http://47.96.190.73:8080`；实际以 `relay.env` 为准 |
| 对外接口 | `/api/levels`（自制关卡）、`/privacy.html`、`/admin`（后台） |

数据目录三个文件：

| 文件 | 内容 | 备注 |
|---|---|---|
| `levels.json` | 自制关卡（`{v:1, levels:{码: 关卡}}`） | 最多 2000 张，超出按创建时间淘汰；单张 64KB、最多 300 个物件 |
| `stats.json` | 联机统计（总量 + 按天计数） | 只存计数，不存 IP / 昵称 |
| `accounts.json` | 后台账号（scrypt 哈希 + 每账号 salt） | 无明文密码；有账号后 `relay.env` 的引导密码不再生效 |

写入方式都是「先写 `.tmp` 再 `rename` 原子替换」。unit 启用了 `ProtectSystem=strict`，只把 `/var/lib/magnetic-rush` 放开为可写，因此**不要把 `DATA_DIR` 改到别处**；确需更改时必须同步修改 unit 的 `ReadWritePaths`。

`relay.env` 支持的键：`PORT`、`HOST`、`DATA_DIR`、`ADMIN_USER`、`ADMIN_PASSWORD`。格式为一行一个 `KEY=VALUE`，值不加引号、不留行尾空格，注释单独占行。

**当前是明文直连内测**：后台密码与 Cookie 都明文过网。内测结束应改为 `HOST=127.0.0.1` + Nginx/Caddy 反代 TLS，并只放行 80/443。

## 2. 首次部署

### 2.1 准备系统与 Node.js

```bash
sudo apt-get update
sudo apt-get install -y curl ca-certificates unzip
# Node 22 LTS（国内慢时可先用系统自带的 nodejs/npm，要求 18+）
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo bash -
sudo apt-get install -y nodejs
node -v && npm -v
```

### 2.2 取得部署包

> 本节起使用 root shell：先 `sudo -i`。`/root/releases` 是 `0700`，普通账号即使加 `sudo` 也无法直接 `cd` 进去。

**方式 A：GitHub Release 附件（推荐，正式版本）**

在 Releases 页面确认版本后，在服务器上执行（把 `<version>` 换成实际版本，例如 `1.2.0`）：

```bash
VER=<version>
sudo install -d -m 0700 /root/releases
cd /root/releases
sudo curl -fL -O "https://github.com/huanmiexinghe/-/releases/download/v${VER}/magnetic-rush-server-linux-${VER}.zip"
sudo curl -fL -O "https://github.com/huanmiexinghe/-/releases/download/v${VER}/SHA256SUMS"
sudo sha256sum -c SHA256SUMS
sudo unzip -q "magnetic-rush-server-linux-${VER}.zip" -d "/root/releases/v${VER}"
```

**方式 B：从仓库源码打包（尚无 Release 时）**

```bash
sudo apt-get install -y git zip   # 若未安装
sudo install -d -m 0700 /root/releases
git clone https://github.com/huanmiexinghe/-.git /tmp/mr-src
cd /tmp/mr-src/deploy
sudo zip -qr /root/releases/magnetic-rush-server-linux-dev.zip linux-server
sudo unzip -q /root/releases/magnetic-rush-server-linux-dev.zip -d /root/releases/dev
```

两种方式最终都应得到一个包含 `app/relay-server.mjs`、`install.sh`、`upgrade.sh`、`rollback.sh`、`check-health.sh`、`relay.env.example` 的目录。**保留这个目录**：`check-health.sh` / `rollback.sh` 不会安装到 `/opt`，后续排查和回滚都要用它。

> Release 包内顶层目录为 `magnetic-rush-server-linux/`；方式 B 从 `deploy/linux-server` 打包，顶层目录是 `linux-server/`。下文命令按 `magnetic-rush-server-linux/` 书写，若你的包目录名不同，按实际名称替换。

### 2.3 安装

```bash
cd /root/releases/v<version>/magnetic-rush-server-linux   # 方式 B 为 /root/releases/dev/linux-server
sudo bash install.sh
```

`install.sh` 会：检查 root / node / npm → 创建 `magnetic-rush` 用户 → 复制程序到 `/opt/magnetic-rush` → `npm ci --omit=dev` → **首次**生成 `/etc/magnetic-rush/relay.env`（随机 16 位后台密码，只打印一次）→ 安装并启动 systemd 服务 → 本机自检 `/api/levels`。

脚本可重复执行：已有的 `relay.env`、`accounts.json`、`levels.json` 不会被覆盖。

**立即把打印出来的后台账号密码存入密码管理器**，之后改密码走 `/admin` → 账号管理。

### 2.4 放行与验证

```bash
# 阿里云安全组放行 TCP 8080（内测直连；来源尽量限制为自己的 IP）
# 服务器本机若启用 ufw：
sudo ufw allow 22/tcp
sudo ufw allow 8080/tcp
sudo ufw status verbose

# 本机健康检查
sudo bash /root/releases/v<version>/magnetic-rush-server-linux/check-health.sh

# 外网验证
curl -m 10 -sS -o /dev/null -w '%{http_code}\n' http://47.96.190.73:8080/api/levels
```

浏览器打开 `http://47.96.190.73:8080/admin`，应 303 跳到 `/admin/login`，用初始账号登录成功即部署完成。

## 3. 标准升级流程

> **升级前必须先做数据快照。** `upgrade.sh` 只备份程序（`/var/backups/magnetic-rush/<时间戳>/`），**不会备份 `/var/lib/magnetic-rush`**，也不会保留 `relay.env`。数据出问题时只能靠你自己的快照。

### 3.1 变更前确认

1. Release 已发布，`SHA256SUMS` 校验通过；
2. 确认本次改动是否涉及数据格式（`levels.json` / `stats.json` / `accounts.json` 的字段变化）。涉及格式变更时，必须阅读第 4.3 节；
3. 通知在线玩家会有短暂断线（升级会重启服务）。

### 3.2 必做：数据快照

```bash
# 短暂停服，保证三个 JSON 是同一时刻的一致状态
sudo systemctl stop magnetic-rush-relay

sudo tar -C /var/lib -czf "/var/backups/magnetic-rush/data-$(date +%Y%m%d-%H%M%S).tar.gz" magnetic-rush

# 校验归档可读且包含三个文件
sudo tar -tzf "$(ls -1t /var/backups/magnetic-rush/data-*.tar.gz | head -n1)" | tail -n 10

sudo systemctl start magnetic-rush-relay
sudo bash /root/releases/v<version>/magnetic-rush-server-linux/check-health.sh
```

归档文件名以 `data-` 开头，`rollback.sh` 只识别 `20*` 的程序备份目录，不会把数据归档误当成程序备份。

### 3.3 解包与升级

```bash
VER=<version>
sudo install -d -m 0700 "/root/releases/v${VER}"
cd /root/releases
sudo curl -fL -O "https://github.com/huanmiexinghe/-/releases/download/v${VER}/magnetic-rush-server-linux-${VER}.zip"
sudo curl -fL -O "https://github.com/huanmiexinghe/-/releases/download/v${VER}/SHA256SUMS"
sudo sha256sum -c SHA256SUMS
sudo unzip -q "magnetic-rush-server-linux-${VER}.zip" -d "/root/releases/v${VER}"

# 参数是「包含 app/ 的新版目录」，不是 zip 文件
sudo bash "/root/releases/v${VER}/magnetic-rush-server-linux/upgrade.sh" "/root/releases/v${VER}/magnetic-rush-server-linux"
```

`upgrade.sh` 会：把当前 `/opt/magnetic-rush` 的程序备份到 `/var/backups/magnetic-rush/<时间戳>/` → 停服务 → 覆盖 `*.mjs`、`public/`、`package*.json` → `npm ci --omit=dev` → 启动 → 自检。**不碰数据目录和 `relay.env`，后台密码不会变。** 只保留最近 5 份程序备份。

### 3.4 升级后验证与留痕

```bash
sudo bash "/root/releases/v${VER}/magnetic-rush-server-linux/check-health.sh"
sudo systemctl status magnetic-rush-relay --no-pager
curl -m 10 -sS -o /dev/null -w '%{http_code}\n' http://47.96.190.73:8080/api/levels
```

全部通过后，按第 8 节记录。若自检失败，脚本会打印 `rollback.sh <时间戳>` 命令，按第 4 节处理，**不要带着失败状态继续操作**。

## 4. 回滚：程序与数据是两件事

### 4.1 程序回滚（只换代码，不动数据与配置）

```bash
# 在保留的部署包目录执行（脚本没有安装到 /opt）
cd /root/releases/v<version>/magnetic-rush-server-linux

sudo bash rollback.sh --list             # 列出可用备份
sudo bash rollback.sh                    # 回到最近一次
sudo bash rollback.sh 20261120-153000    # 回到指定时间戳
```

`rollback.sh` 会停服 → 用备份覆盖 `*.mjs`、`public/`、`package*.json` → `npm ci --omit=dev` → 启动 → 自检。**不碰 `/var/lib/magnetic-rush`，不碰 `/etc/magnetic-rush/relay.env`。** 备份目录由 `upgrade.sh` 生成，只保留 5 份。

### 4.2 数据回滚（恢复快照）

只在确认数据被写坏、或跨数据格式回滚时执行：

```bash
sudo systemctl stop magnetic-rush-relay

# 先保留现场，避免恢复错了无法回头
sudo mv /var/lib/magnetic-rush "/var/lib/magnetic-rush.broken-$(date +%Y%m%d-%H%M%S)"

sudo tar -C /var/lib -xzf /var/backups/magnetic-rush/data-20261125-101500.tar.gz
sudo chown -R magnetic-rush:magnetic-rush /var/lib/magnetic-rush
sudo chmod 0750 /var/lib/magnetic-rush

sudo systemctl start magnetic-rush-relay
sudo bash /root/releases/v<version>/magnetic-rush-server-linux/check-health.sh
```

注意：

- 归档是用 `-C /var/lib` 打包的，解压也必须 `-C /var/lib`；
- 解压后必须恢复属主，否则服务用户写不了数据；
- 恢复会覆盖停服之后产生的所有新关卡与新统计，操作前确认备份时间点。

### 4.3 数据格式变更后的注意事项

1. **先快照再升级**。涉及格式变更的版本，3.2 节的快照是回滚的唯一退路。
2. **程序回滚不会回滚数据**。新版本可能已经用新格式重写了 `levels.json` / `stats.json` / `accounts.json`；此时只执行 `rollback.sh` 回到旧代码，旧代码读新格式可能丢字段、读不出数据，或直接以空库启动。
3. **跨格式回滚要成对操作**：旧程序 + 对应时间点的数据快照。先 `rollback.sh <时间戳>`，再按 4.2 恢复该时间点（或升级前）的数据快照。
4. **加载逻辑是「容错」而不是「报错」**：`levels.json` / `stats.json` 损坏或字段不合法时，服务会从空数据启动；`levels.json` 一旦在空库状态下被新上传触发写入，原文件会被覆盖。发现数据异常时**先停服、先备份文件、再动代码**。
5. `accounts.json` 损坏或为空时，服务会尝试用 `relay.env` 的 `ADMIN_USER` / `ADMIN_PASSWORD` 重新创建引导管理员；这能救回登录，但会丢失原有账号（以及各自的密码）。恢复前先备份损坏文件。
6. 新版确认稳定前，不要手工删除 `/var/backups/magnetic-rush` 里的程序备份与 `data-*.tar.gz`。

## 5. 健康检查与日志排查

### 5.1 一键检查

```bash
sudo bash /root/releases/v<version>/magnetic-rush-server-linux/check-health.sh
```

脚本依次检查：systemd 是否 `active` → 是否监听 `PORT` → `/api/levels` 200 → `/privacy.html` 200 → `/admin/login` 200 → `/admin` 200/303 → WebSocket 是否收到 `hello`。退出码非 0 时会自动打印最近 40 行日志。

### 5.2 手动逐项

```bash
sudo systemctl status magnetic-rush-relay --no-pager
sudo ss -lntp | grep :8080
curl -sS -m 5 -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/levels
curl -sS -m 5 -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/privacy.html
curl -sS -m 5 -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/admin/login
curl -sS -m 5 -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/admin   # 期望 200 或 303

# 外网（排除安全组 / 防火墙问题）
curl -m 10 -sS -o /dev/null -w '%{http_code}\n' http://47.96.190.73:8080/api/levels

# 如果是反代模式，再验证 80/443 的 HTTP 可达性（WebSocket 升级头需用客户端或 wscat 另测）
curl -m 10 -sSI http://<域名>/api/levels
```

### 5.3 日志

```bash
sudo journalctl -u magnetic-rush-relay -n 100 --no-pager      # 最近 100 行
sudo journalctl -u magnetic-rush-relay -f                     # 实时
sudo journalctl -u magnetic-rush-relay --since "30 min ago" --no-pager
sudo journalctl -u magnetic-rush-relay -p err -n 50 --no-pager
```

常见现象：

| 现象 | 可能原因 | 处理 |
|---|---|---|
| `systemctl status` 为 `failed` | 启动即崩 | 看 journal 第一条错误；检查 `relay.env` 格式、Node 路径、数据目录权限 |
| 日志提示端口被占用 | 旧进程 / 其他程序 | `sudo ss -lntp \| grep :8080`，停掉占用后 `systemctl restart` |
| 本机 curl 通、外网超时 | 安全组或 ufw 未放行；`HOST=127.0.0.1` | 两层都放行；直连模式需 `HOST=0.0.0.0` |
| HTTP 200 但手机连不上 | 只验证了 HTTP，WS 不通 | 跑 `check-health.sh` 看 `hello`；查反代 WS 升级头 |
| `/admin` 提示后台未初始化 | 没有账号且 `relay.env` 无引导账号 | 配 `ADMIN_USER` / `ADMIN_PASSWORD` 后重启（仅零账号时生效） |
| 日志 `EACCES` / 写入失败 | 数据目录属主或权限被改 | `chown -R magnetic-rush:magnetic-rush /var/lib/magnetic-rush`；`chmod 0750` |

## 6. 备份与还原

### 6.1 何时备份

- **每次升级前必须**（第 3.2 节）；
- 修改 `relay.env`、账号、批量删关卡之前；
- 建议每日定时备份并异地保存（cron 或 systemd timer 均可）。

### 6.2 手动备份

```bash
sudo systemctl stop magnetic-rush-relay
sudo tar -C /var/lib -czf "/var/backups/magnetic-rush/data-$(date +%Y%m%d-%H%M%S).tar.gz" magnetic-rush
sudo systemctl start magnetic-rush-relay
sudo tar -tzf "$(ls -1t /var/backups/magnetic-rush/data-*.tar.gz | head -n1)" | tail -n 5
```

程序本身不需要备份：源码在仓库，二进制在 Release，`upgrade.sh` 还会自动留 5 份程序备份。

### 6.3 清理旧归档

`upgrade.sh` 只会清理程序备份（`/var/backups/magnetic-rush/20*`），不清理 `data-*.tar.gz`。清理前先预览：

```bash
sudo find /var/backups/magnetic-rush -maxdepth 1 -name 'data-*.tar.gz' -mtime +14 -print
```

确认列表无误后，再把 `-print` 换成 `-delete`。

### 6.4 还原

见第 4.2 节。还原后务必跑 `check-health.sh`，并让玩家实际创建/加入一次房间验证 WebSocket。

## 7. 应急处理

总原则：**先止血（轮换凭据 / 停服 / 断网），再取证，再清理，最后复盘。** 公开仓库里出现过的凭据一律按「已泄露」处理，删除提交不等于没泄露。

### 7.1 凭据泄露

**管理员密码泄露**

```bash
# 首选：登录后台改密
# http://47.96.190.73:8080/admin → 账号管理 → 重置密码
```

若已无法登录：

```bash
sudo systemctl stop magnetic-rush-relay
sudo cp -a /var/lib/magnetic-rush/accounts.json /var/backups/magnetic-rush/accounts.broken-$(date +%Y%m%d-%H%M%S).json
# 方案一：按 accounts.mjs 的存储格式修复/重置目标账号
# 方案二：确认 relay.env 里 ADMIN_USER / ADMIN_PASSWORD 可用后，移走 accounts.json，
#         让服务在「零账号」状态下用引导账号重建（会丢失现有全部账号）
sudo mv /var/lib/magnetic-rush/accounts.json /var/backups/magnetic-rush/accounts.removed.json
sudo systemctl start magnetic-rush-relay
```

> 用方案二重建前，确认 `relay.env` 里的引导密码不是泄露的那个；如果它也泄露了，先改 `relay.env`、`systemctl restart`，再走重建。

**`relay.env` 泄露**：`ADMIN_PASSWORD` 只影响「零账号」引导；仍应改掉后台实际密码、收紧文件权限 `chown root:magnetic-rush` / `chmod 0640`，并检查是否有异常登录。

**cpolar authtoken 泄露**：登录 cpolar 后台 revoke 旧 token，重建隧道，更新本机配置；旧域名立即停用。

**GitHub PAT 泄露**：GitHub → Settings → Developer settings → 删除该 token；检查仓库近期提交与 Release 是否被篡改。

**SSH 私钥泄露**：从服务器对应用户的 `~/.ssh/authorized_keys` 删除该公钥，`sudo systemctl reload ssh`；检查 `sudo journalctl -u ssh --since` 与 `/var/log/auth.log` 是否有异常登录。

### 7.2 误把敏感文件推上公开仓库

顺序固定，不要颠倒：

1. **先轮换**涉及的密码 / token / 密钥（泄露已成事实，清理历史不会让看过的人失忆）；
2. 评估暴露窗口：`git log --oneline -- <路径>`，查 GitHub 的 commit / Release / Actions 记录；
3. 清理历史（任选其一，操作前先完整 clone 备份）：
   ```bash
   # 需要 git-filter-repo：python3 -m pip install --user git-filter-repo
   git filter-repo --path <敏感文件路径> --invert-paths
   ```
   或在本地重置到干净提交后重建历史；
4. 强推 `main`：分支保护开启后需临时加 bypass，强推完立即移除；通知所有协作者重新同步；
5. 联系 GitHub Support 清理缓存视图；**已产生的 fork 无法回收**，只能继续依赖轮换；
6. 在 Release / 团队记录里写清时间、文件、轮换动作。

### 7.3 服务起不来

按顺序排查，不要一上来就重装：

```bash
sudo systemctl status magnetic-rush-relay --no-pager
sudo journalctl -u magnetic-rush-relay -n 100 --no-pager
sudo ss -lntp | grep :8080
sudo df -h /var/lib /opt
sudo ls -l /var/lib/magnetic-rush
sudo cat /etc/magnetic-rush/relay.env      # 确认格式：无引号、注释单独占行、无行尾空格
```

处理分支：

- 端口占用 → 停占用进程或改 `PORT`（改后 `systemctl restart`）；
- 数据目录权限错 → `chown -R magnetic-rush:magnetic-rush /var/lib/magnetic-rush` 后重启；
- 磁盘满 → 清理旧 `data-*.tar.gz` 与 journal（`sudo journalctl --vacuum-time=7d`）；
- 新版本启动即崩 → `rollback.sh` 回程序；
- 数据文件损坏 → 先停服备份损坏文件，再按 4.2 恢复快照；
- 都不行 → 用最近的部署包重新 `install.sh`（不会覆盖数据与 `relay.env`）。

### 7.4 数据异常

先停服，再复制现场，再恢复。**不要在服务运行时手工编辑 JSON**，也不要在空库状态下让服务继续接收上传（会覆盖 `levels.json`）。

### 7.5 服务器疑似被入侵

1. 阿里云安全组先封 `8080`、`22`（仅保留自己的 IP）；
2. 打快照留证，不要立即重装；
3. 轮换全部凭据（后台密码、cpolar、SSH、GitHub）；
4. 检查 `/opt/magnetic-rush` 与 `public/` 是否被篡改：把 Release 包 `app/` 下的 `*.mjs`、`public/*.html` 与 `/opt/magnetic-rush` 逐文件 `sha256sum` 比对；
5. 复盘后重装系统，按第 2 节重新部署。

## 8. 权限、操作与留痕

### 8.1 谁能操作

- **Operator（2 人）**：持有服务器 SSH 密钥、sudo 权限、阿里云控制台权限（开 MFA）。日常只做状态查看、重启、日志排查；安装/升级/回滚需两人知晓。
- **Maintainer（2 人）**：合并 `main`、发 Release；默认不持有 SSH。
- **Developer**：无生产权限，只能通过 PR 影响代码。

SSH 要求：一人一把 ed25519 密钥，禁止共享；服务器关闭密码登录（`PasswordAuthentication no`），`PermitRootLogin prohibit-password`；人员变动立即移除公钥与 sudo 组。

### 8.2 部署目录

发布包统一解压到 root 专属目录，不要用 `/tmp` 里他人可写的目录执行 root 脚本：

```bash
sudo install -d -m 0700 /root/releases
```

### 8.3 每次操作留痕

三处同时记录：

1. **服务器部署日志**：

   ```bash
   sudo sh -c 'printf "%s\t%s\t%s\t%s\n" "$(date -Is)" "$(whoami)" "v1.2.0" "升级完成，自检通过" >> /var/backups/magnetic-rush/deploy-log.tsv'
   sudo cat /var/backups/magnetic-rush/deploy-log.tsv
   ```

2. **GitHub Release 评论**：在对应 Release 下写「已部署 47.96.190.73 / 操作人 / 时间 / 结果」。

3. **journald 与 auth 日志**：`journalctl -u magnetic-rush-relay` 与 `/var/log/auth.log`（记录 sudo 调用），默认保留即可，排障时按时间检索。

建议把「升级前数据快照 + 部署日志 + Release 评论」视为一次完整上线的三个必做动作，缺一不可。
