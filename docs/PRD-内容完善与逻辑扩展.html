00评审摘要

现有游戏已经是一个可完整游玩的成品：30 个常规关、3 个特殊关、1 个彩蛋关、无尽模式、4 人联机竞速、自定义关卡编辑器、14 类关卡元素、10 个成就。真正缺的不是“能不能玩”，而是“为什么再玩一遍”与“失败后能否继续”。

本设计把问题收敛为三条主线：

  1. 目标线：把每关变成“★1 通关 / ★2 全晶片 / ★3 连击目标”，让已经存在于 LevelDef.maxCombo 但从未被读取的字段真正发挥作用。
  2. 公平线：修掉“狂按切换就能刷连击”的规则漏洞；把“漏 1 个晶片就整关重开”的硬门槛改成星级目标；让触屏玩家也能在连续失败后跳关。
  3. 内容线：新增第 7–8 章共 12 关、3 种新障碍（移动浮台 / 相位墙 / 脉冲激光）、无尽 2.0 分区与磁暴事件、每日挑战、纯外观成长线。
本次只交付设计，不改游戏代码。所有数值均为首发默认值，标注 [TBD] 的项需要在实现后联调校准。文档中的“新增”均已与现有代码逐条比对，已实现内容只作为基线陈述，不重复立项。

需要用户确认的 5 个核心决策

1

连击是否改为“有效事件计数”，删除“切换即 +1”

推荐：改。现在 Player.switchPolarity() 每切换一次就 combo++，配合 0.18s 冷却，约 9 秒即可刷到 50 连击并触发最高速度加成与成就。改后只有“安全通过危险 / 收集 / 穿门 / 过区”才计数。影响：手感不变，但星级目标、成就、无尽纪录的含金量全部改变。

2

终点“必须集齐全部晶片”是否改为星级条件

推荐：改。现在漏收晶片会在终点触发 die()，普通关没有检查点，等于整关重开；而晶片大量放在可选高台，容错极低。改为“终点永远可通，缺片只影响 ★2”，把惩罚从“重开”降为“少一颗星”。影响：关卡难度曲线整体下降，需同步调整 ★3 连击目标。

3

本期内容规模：只做 P0 闭环，还是一次做到第 8 章

推荐：分两步。第一步 P0 + P1（星级/连击/补救/跳关 + 第 7 章 31–36 + 3 新机制 + 无尽 2.0 + 每日挑战）；第二步再评估第 8 章 37–42、外观、联机扩展。影响：直接决定本次实现批次与验收范围。

4

成长线是否允许永久数值升级

推荐：不允许，只做外观。永久加速/额外生命/自动收集会直接破坏竞速、每日挑战与无尽纪录的可比性，也会让 ★3 目标失去意义。磁芯只兑换皮肤花纹、尾迹、HUD 框与称号，极性红/蓝本身不可改色。影响：决定经济系统是否需要与数值系统隔离。

5

联机投入深度：轻量增强，还是做淘汰赛 + 服务端校验

推荐：先做轻量增强（重连、重赛、快捷短语、基础成绩校验），淘汰赛放 P2。当前服务端只是转发 15Hz 状态，玩家端权威；做完整服务端权威模拟成本远高于玩法收益。影响：决定是否改 relay-server.mjs 的房间协议。

明确不做（本期范围外）

  • 不做内购、广告、抽卡、体力；磁芯只能由游玩获得。
  • 不做永久数值成长（移速、额外生命、自动收集、复活次数），避免破坏竞速与星级。
  • 不做服务端权威物理模拟；联机保持“客户端权威 + 轻量校验”的休闲定位。
  • 不做小程序重写；仅在第 6 节给出可行性评估。
  • 不做渲染层重构（Canvas 2D 与现有卡通主题保持不变）。
设计原则：新机制必须与“红蓝极性”正交——要么改变空间（平台、墙体），要么改变时间（激光节拍）。不要新增第三种颜色或第三套状态，否则会稀释“同色安全”的核心记忆点。

3.1 状态流转

3.2 星级与连击的唯一口径

以下两条公式是全文档的唯一来源，所有界面、成就、奖励都复用它们，避免同一关出现两套判定。

星级公式（每局独立计算）：
stars = clear ? (1 + allGems + comboGoal) : 0
其中 allGems = (totalGems === 0 || collectedGems === totalGems)，comboGoal = (targetCombo === 0 || runMaxCombo >= targetCombo)；targetCombo 取该关 LevelDef.maxCombo。存档只保留历史最高的 stars，永不下降。
连击来源（新版）：只有“有效通过”才 +1。切换极性本身不再加分。
+1 安全通过同色尖刺（触发安全粒子，未靠无敌帧）　 +1 跳过灰墙　 +1 摆球从身后越过且未死亡　 +1 收集晶片 / 磁芯　 +2 首次穿过一对传送门　 +1 强制极性区退出且未死亡
死亡清零；关卡内不衰减；里程碑 5/10/20/30/50 与速度加成 20/30/50 保持不变。

3.3 存档、奖励与解锁

规则口径为什么这样定
关卡解锁完成上一关（★1 或跳过）即解锁下一关；跳过不产生星沿用现有 isUnlocked 逻辑，不新增门槛，避免玩家因星数被卡住
星级写入只增不减；跳过关首次重打可正常得星现有 recordCompletion 在跳过关重打时会清除跳过标记
磁芯发放某关首次达到 ★1 / ★2 / ★3 时各发 1 枚；重复通关不再发用“首次达到”而不是“每次通关”，避免刷低难度关
每日奖励每日首次完成挑战发 3 枚；当天后续只更新最好成绩鼓励每天来一次，不强迫多次
存档版本新增 version: 2；旧档迁移时仅把“已通关”折算为 ★1，不补发 ★2/★3 与磁芯不追溯奖励，避免老玩家一上线获得大量货币；旧 maxComboEver 保留展示，但因旧连击可刷，不作为任何新判定依据
失败定义任一非豁免碰撞；终点漏片不再算失败（改为少星）把“惩罚”和“目标”分开，失败只保留真正的操作失败
存档迁移必须做幂等：迁移只执行一次；若写入失败不得清空旧档。当前存档键为 magnetic_rush_save_v1，新档建议保留同键并升级字段（或新键 + 旧键只读回退），实现前需确认。

FR-02 连击系统重构 P0 中

目标：让连击只奖励“真的穿过了危险”，而不是“按键够快”。这同时是 ★3 目标成立的前提。

事件旧规则新规则判定条件
切换极性+10仍然保留 0.18s 冷却与 0.1s 容错无敌，仅不加分
通过同色尖刺通过即 +1+1该尖刺已置 triggered = true，且玩家未处于无敌帧；靠无敌硬穿异色尖刺不给分
跳过灰墙通过即 +1+1墙体右缘越过玩家且本帧未死亡；贴地撞墙不触发
摆锤越过+1+1摆球中心越过玩家 x 且玩家存活；仅在摆锤“通过”标记首次写入时计一次
收集晶片 / 磁芯0+1每个物件只计一次；磁芯仅在无尽出现
首次穿传送门0+2该 portalId 首次被使用；重复进入不再计分
强制极性区0+1退出区域边界时仍在世；被强制后撞死不计
死亡清零清零沿用 Player.reset()；复活后从 0 开始
实现要点：当前 GameScene 用一个 passedObstacles 集合对尖刺/墙/摆锤做“首次越过”拦截，直接复用它作为加分幂等键即可，不需要新集合。移除 Player.ts:86–95 中的 combo++ 后，所有既有里程碑、速度加成、彩虹特效都会自动只对有效连击生效。

边界

  • 连击达到 50 后的彩虹态保持到死亡，不因切换而中断（与现有一致）。
  • 加速带、星门不额外给连击，避免“奖励再奖励”。
  • 旧存档的 maxComboEver 可能因刷切换而偏高：保留展示，但结算页不据此发任何奖励；成就 COMBO_KING 若已解锁不回退。
  • 联机模式同样使用新口径；服务端只转发客户端上报的连击，不做校验（休闲定位）。

依赖与改动范围

  • Player.ts:86–95：删除切换加分。 小
  • GameScene.ts:660–869 checkObstacles：按事件源加分；尖刺需判 triggered。 中
  • GameScene.ts:871–885：里程碑/速度加成逻辑不变，仅输入变干净。 小
  • GameScene.ts:1082–1222：HUD 连击显示不变，可增加“目标连击”小字。 小

FR-06 三种新障碍机制 P1 大

目标：增加“空间移动”和“时间节拍”两个维度，但不新增颜色、不新增操作。三种机制都可以用现有 Obstacle 结构 + meta 参数实现。

A. 移动浮台 MOVING_PLATFORM

字段规则默认值 / 范围
运动轴axis: 'x' | 'y'；默认垂直y
位移相对初始位置的振幅，正弦往复60–140 px
周期完整往返时间；同关多个浮台必须错开相位2.4–4.0 s
相位phase: 0–1，用于错开0 / 0.33 / 0.66
位置公式pos = base + sin(2π · t / period + phase · 2π) · range基于关卡时间 t，保证每日/回放确定性
碰撞单向支撑：仅当玩家下落且脚部高于台面时站立；不造成伤害沿用 Player.ts:186–199
携带垂直运动时把玩家 y 同步位移，vy = 0；水平运动不推动玩家 x防止玩家被平台“横推”穿过墙体

边界：平台不得与尖刺/墙/激光在任意相位下重叠；不得作为传送门出口的唯一落点（出口必须有静态安全落点）。浮台越界时 clamp 在 [CEILING+40, GROUND]。

B. 相位墙 POLARITY_WALL

字段规则默认值
墙色polarity: 'RED' | 'BLUE'，外观为半透明条纹 + 极性符号随关卡主题
同色通过不致死，墙在接触处淡出并标记 triggered；给 +1 连击—
异色碰撞立即死亡，无视 0.1s 切换无敌与灰墙同级的“硬规则”
视觉预判墙前 320px 内不得有其他需要切换的障碍—

为什么不用现有 WALL：灰墙是“跳过去”的空间障碍；相位墙是“换颜色穿过去”的极性障碍。两者并列存在，才能让玩家同时练习两条规则。

C. 脉冲激光 PULSE_LASER

字段规则默认值 / 范围
朝向orientation: 'V' | 'H'；V 为顶天立地光柱，H 为贴近地面的横向光束V
周期预警 → 激活 → 冷却 的完整循环2.4–3.2 s
预警细线闪烁，不致死；给玩家明确的“要来了”0.8 s（不得低于 0.8）
激活粗光束，致死0.4–0.6 s
相位同一关的光柱按 x 坐标错开，形成可记忆的节拍由 x / 400 推导
H 型光束贴地 42px 高，跳过即可；激活时仍致死宽 160–260
公平性传送门出口后 250px 内不得放置激光；激光预警开始时若玩家已无法跳跃（空中），仍保证 0.8s 窗口—

时间基准：激光开关必须由关卡累计时间 gameTime 计算，不能使用 performance.now() 或每帧累加计时器。否则死亡重试、每日种子回放会出现相位漂移，联机也无法对齐。

渲染与碰撞扩展点：三种机制都加在 ObstacleKinds 联合类型与 Obstacle.ts:143–188 的 render switch；碰撞在 GameScene.ts:660–869 增加三个分支。移动/时间状态建议放 Obstacle.updateMotion(t)，避免散落在 update 循环里。

依赖与范围：Obstacle.ts:9–16（联合类型）、Obstacle.ts:143–188（渲染）、GameScene.ts:660–869（碰撞）、EditorScene.ts（工具栏）、CustomLevels.ts:21–25（合法类型/清洗）。 大

目标：让一局无尽在 2 分钟内至少经历一次“区域变化”和一次“磁暴事件”，把单调的间距缩放变成有起伏的跑图体验。

拾取与事件

  • 磁芯：复用 COLLECTIBLE，meta.currency = 1；每约 1500px 生成一组 3–5 枚弧线，收集 +1 连击、+1 磁芯；不计入 totalGems，不影响终点（无尽无终点）。
  • 护盾：复用 SPECIAL_ITEM 并设 meta.itemId = 'SHIELD'；每约 9000px 生成 1 个；最多持有 1 层；触发后免除一次致命碰撞并给 3s 无敌，HUD 显示盾牌图标。 P2
  • 磁暴事件：每 50s 触发一次，持续 12s：速度系数 +0.12，生成密度 +20%，磁芯价值 ×2，屏幕边缘出现红色脉冲（可关闭）。事件开始/结束各有一条横幅。

死亡即结束，结算显示：跑距、存活时间、最高连击、到达区域、获得磁芯、是否刷新个人最好。现有无尽结算页已显示时间/距离/连击，新增“区域/磁芯”两行即可。

不做每日种子对齐时：无尽仍使用随机生成。每日挑战（FR-08）会传入固定种子，因此生成器必须支持 seed 参数；建议把现有 Math.random() 调用统一替换为可注入的伪随机函数，这是无尽 2.0 与每日挑战的共同前置。

06小程序端可行性

结论：本期不建议做小程序端。本项目是 Vite + Canvas 2D + Capacitor 壳的 Web 游戏，不是 Taro 小程序工程。miniapp-builder 插件面向 Taro 小程序的预览、诊断与上传，直接套用无法产生可运行的小程序包；为“用插件”而改造现有工程，投入产出比不成立。

技术依赖对比

能力当前实现小程序环境改造代价
渲染Canvas 2D 全量绘制（场景、HUD、编辑器都在 canvas 上）微信小游戏可用 wx.createCanvas；小程序页面的 canvas 组件尺寸/层级受限需要 canvas 适配层；若走小程序页面还要处理组件层级与全屏
音频WebAudio 程序化合成音效与音乐（Audio.ts）小游戏为 InnerAudioContext，不支持完整 WebAudio 节点图大：需要改为音频文件/精灵，或重写合成层
存档localStorage 单键 JSON（SaveSystem.ts）wx.setStorageSync / getStorageSync小：封装一层存储适配即可
联机浏览器 WebSocket 连 wss 中继（OnlineManager.ts）wx.connectSocket，需配置服务器域名白名单中：API 替换 + 域名备案/白名单
输入键盘 + Pointer 事件 + 画布内虚拟按键（Input.ts）触摸事件小：现有触屏路径已存在
DOM 浮层联机昵称/房间输入使用 HTML 浮层无 DOM中：需改为小程序输入组件或画布内输入
打包Vite 构建 + Capacitor 生成 APKTaro/原生小游戏工程大：构建链与目录结构都要换

三个可选路径

路径做法优点风险 / 代价建议
A. web-view 内嵌 H5 保留现有工程，发布 H5；小程序用一个 web-view 页面打开 代码几乎不改；APK 与 H5 同一套逻辑 需要业务域名、ICP 备案、类目与游戏内容审核；web-view 能力受平台规则限制，分享/登录体验弱 若必须做，先做这条试点
B. 微信小游戏重写 以 wx.createCanvas 为入口，替换音频、存储、网络、输入适配层 体验最接近原生小游戏，可接平台分享/排行榜 渲染循环、音频、UI 浮层、构建链全部要改；等于第二个客户端 不建议本期
C. Taro 小程序工程 用 Taro 重建页面与 canvas 容器，复用部分纯逻辑模块 可跨微信/支付宝/抖音 Taro 不解决 Canvas 渲染与 WebAudio 差异；仍要重写大部分表现层 不建议
结论口径：小程序的真正门槛不在代码量，而在“账号体系 + 域名备案 + 游戏类目审核 + 音频/渲染适配”。在没有明确的小程序分发需求前，这部分投入不会改善当前 APK 的核心体验。若未来要做，建议单独立项，并以“H5 + web-view 试点”验证留存后再决定是否重写。
